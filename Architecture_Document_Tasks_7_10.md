# Архитектурный документ: проектирование и миграция данных для интернет-магазина «Мобильный мир»

## 1. Введение

Документ описывает архитектурные решения для трёх ключевых сущностей (товары, заказы, корзины) в условиях высокой нагрузки (50 000 запросов/сек). Рассмотрены шардирование в MongoDB, чтение с реплик, мониторинг горячих шардов, а также миграция части нагрузки на Cassandra для обеспечения линейной масштабируемости.

## 2. Задание 7. Проектирование схем коллекций MongoDB для шардирования

### 2.1 Коллекция `products` – товары

**Схема документа** (JSON / BSON):

```mongodb-json
{
  "_id": ObjectId("..."),
  "sku": "PH-1001-X",
  "name": "Смартфон X",
  "category": "Электроника",
  "price": 49990,
  "stock": {
    "Москва": 120,
    "Санкт-Петербург": 45,
    "Екатеринбург": 50,
    "Калининград": 30
  },
  "attributes": {
    "color": "черный",
    "memory": "128GB",
    "screen": "6.5\""
  },
  "created_at": ISODate("..."),
  "updated_at": ISODate("...")
}
```

#### Анализ операций
- **Частые обновления остатков** при покупках (запись по _id, изменение вложенного поля `stock.геозона`).
- **Поиск по категориям и фильтрация по цене** (диапазон).
- **Чтение описания товара** (по _id или sku).

**Шард-ключ**: `{ "_id": "hashed" }`  
**Стратегия**: хешированный ключ по `_id`.

**Предложение**:
- Шардировать по `{ _id: "hashed" }` – для максимальной равномерности при записи и обновлении остатков (операции идут по _id).
- Для поиска по категориям и цене создать **вторичные индексы** и принимать broadcast запросы, либо использовать покрывающие индексы.
- Учитывая, что товаров много (миллионы), обновления остатков происходят по каждому заказу – это высоконагруженная операция, и важно, чтобы они не вызывали горячих точек. Хешированный `_id` идеален.

**Обоснование**:
- Равномерное распределение вставок и обновлений по шардам.
- Обновление остатка выполняется по _id – запрос идёт точно в один шард.
- Поиск по категориям и цене – можно обслуживать с помощью глобального индекса или покрывающего индекса `{ category: 1, price: 1 }`. Небольшой оверхед на broadcast-запросы допустим, так как категорий ограниченное количество, и товаров в категории может быть много, но запросы не очень частые по сравнению с обновлениями остатков.

**Пример команды**:

```javascript
sh.enableSharding("shop")
sh.shardCollection("shop.products", {"_id": "hashed"})
```

**Индексы** для ускорения поиска:

```javascript
//- `{ category: 1, price: 1 }` – фильтрация каталога.
db.products.createIndex({category: 1, price: 1})
//- `{ sku: 1 }` – поиск по артикулу.
db.products.createIndex({sku: 1})
```

| Преимущества                                              | Риски                                                                                                  |
|-----------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| Равномерное распределение вставок и обновлений по шардам. | Запросы по категориям и цене требуют broadcast (scatter/gather).                                       |
| Отсутствие «горячих» точек при записи.                    | При очень частых запросах на фильтрацию может потребоваться дополнительный индекс или изменение ключа. |

### 2.2 Коллекция `orders` – заказы

**Схема документа**:

```mongodb-json
{
  "_id": ObjectId("..."),
  "user_id": ObjectId("..."),
  "created_at": ISODate("..."),
  "items": [
    { "product_id": ObjectId("..."), "quantity": 2, "price": 49990 }
  ],
  "status": "paid",
  "total": 101180,
  "geo_zone": "Москва"
}
```

#### Анализ операций
- **Быстрое создание заказов** (высокая интенсивность вставки).
- **Поиск истории заказов конкретного пользователя** (`user_id`).
- **Отображение статуса заказа** (по _id или по user_id + _id).

**Шард-ключ**: `{ "user_id": "hashed" }`

**Предложение**: **хешированный шард-ключ по `user_id`**.  
Это обеспечит равномерное распределение нагрузки по пользователям, а запрос истории заказов будет выполняться на одном шарде (без broadcast).  
Создание заказа – вставка, также попадёт в шард по хешу user_id.  
Статус заказа можно получать по составному индексу `{ user_id: 1, _id: 1 }`, запрос также попадёт в нужный шард.

**Стратегия**:  
`sh.shardCollection("shop.orders", { "user_id": "hashed" })`

**Обоснование**:
- Основная операция поиска истории заказов пользователя – критична для UX, должна быть быстрой и не пересекать все шарды.
- Вставки распределяются равномерно, так как user_id распределён хешем.
- Статус заказа можно получить через `find({ _id: id, user_id: uid })` – MongoDB использует шард-ключ user_id для маршрутизации.
- Геозона в ключе не участвует, так как не является частым критерием.

**Пример команды**:

```javascript
sh.shardCollection("shop.orders", {"user_id": "hashed"})
```

**Индексы** для ускорения поиска:

```javascript
db.orders.createIndex({user_id: 1, _id: 1, status: 1})
```

| Преимущества                                                                  | Риски                                                                                                                        |
|-------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------|
| История заказов пользователя читается с одного шарда (быстро, без broadcast). | Очень активный пользователь создаст большую партицию – возможен перекос. Решение: бакетирование по времени (см. раздел 4.2). |
| Равномерное распределение вставок за счёт хеширования user_id.                | –                                                                                                                            |

### 2.3 Коллекция `carts` – корзины

**Схема документа**:

```mongodb-json
{
  "_id": ObjectId("..."),
  "user_id": "session_12345",        
  "session_id": "session_12345",    
  "items": [
    { "product_id": ObjectId("..."), "quantity": 1 }
  ],
  "status": "active",
  "created_at": ISODate("..."),
  "updated_at": ISODate("..."),
  "expires_at": ISODate("...")       
}
// user_id = для гостя = session_id а для авторизованного = ObjectId
// expires_at -> TTL
```

#### Анализ операций

- **Создание корзины** по session_id (гость) или user_id (пользователь).
- **Поиск активной корзины** по `{ session_id, status:"active" }` или `{ user_id, status:"active" }`.
- **Добавление/замена товара** (обновление).
- **Удаление товара** (обновление).
- **Слияние гостевой корзины в пользовательскую** (чтение одной, обновление другой, изменение статуса гостевой).
- **Отметка корзины как ordered** (обновление).
- **TTL** – автоматическое удаление по `expires_at`.

**Шард-ключ**: `{ "user_id": "hashed" }` (унифицирован – для гостей в поле `user_id` хранится `session_id` + префикс).

**Пример команды**:

```javascript
sh.shardCollection("shop.carts", {"user_id": "hashed"})
```

**Индексы** для ускорения поиска:

```javascript
db.carts.createIndex({user_id: 1, status: 1})
db.carts.createIndex({expires_at: 1}, {expireAfterSeconds: 0})
```

| Преимущества                                                                                            | Риски                                                                                                |
|---------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| Любая операция с корзиной (чтение, обновление) выполняется на одном шарде – высокая производительность. | Слияние гостевой корзины в пользовательскую может потребовать межшардного запроса (редкая операция). |
| Автоматическая очистка по TTL работает на уровне документа.                                             | –                                                                                                    |

## 3. Задание 8. Выявление и устранение «горячих» шардов

### 3.1 Метрики мониторинга

| Метрика                                            | Инструмент                         | Порог срабатывания                      |
|----------------------------------------------------|------------------------------------|-----------------------------------------|
| Количество операций чтения/записи на шард (оп/сек) | `mongostat --discover`             | Отклонение >30% от среднего по кластеру |
| Размер очереди операций                            | `db.currentOp().inprog.length`     | >100                                    |
| Загрузка CPU на сервере шарда                      | Prometheus + node_exporter         | >80% в течение 5 минут                  |
| Медленные запросы (>100 мс)                        | Slow query log                     | >10 в минуту                            |
| Задержка репликации (secondary lag)                | `rs.status().members[].optimeDate` | >5 секунд                               |

**Пример сбора метрик**:

```bash
mongostat --discover --host mongos -n 10
```

### 3.2 Механизмы перераспределения данных

| Проблема                                 | Решение                                                                                                                                                                                                              | Команды                      |
|------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------|
| Перекос чанков                           | Автоматическая балансировка (включена по умолчанию)                                                                                                                                                                  | `sh.setBalancerState(true)`  |
| Горячая категория товаров (70% запросов) | Добавить кеширование (Redis) + read preference secondary                                                                                                                                                             | –                            |
| Один шард перегружен                     | Увеличить количество чанков (уменьшить `chunkSize`) или добавить зону шардирования                                                                                                                                   | `sh.updateZoneKeyRange(...)` |
| Добавление нового шарда                  | **MongoDB**: балансировщик перемещает чанки **со всех существующих шардов** на новый, что может вызвать временную нагрузку. **Cassandra**: перераспределяются только соседние диапазоны токенов, что менее затратно. | –                            |

**Пример настройки зоны для категории «Электроника»** (при шард-ключе `{ category: 1, _id: 1 }`):

```javascript
sh.addShardToZone("shard1", "electronics_zone")
sh.addShardToZone("shard2", "electronics_zone")
sh.updateZoneKeyRange("shop.products",
    {category: "Электроника", _id: MinKey},
    {category: "Электроника", _id: MaxKey},
    "electronics_zone")
```

**Рекомендация**: для текущего хешированного ключа по `_id` – использовать кеширование и read preference, а не зоны.

## 4. Задание 9. Настройка чтения с реплик и консистентность

### 4.1 Таблица операций: primary / secondary

| Коллекция | Операция                                     | Чтение с secondary | Допустимая задержка | Обоснование                                         |
|-----------|----------------------------------------------|--------------------|---------------------|-----------------------------------------------------|
| products  | Поиск по категориям/цене (каталог)           | ✅ да               | ≤5 сек              | Пользователь не заметит устаревшие цену или остаток |
| products  | Проверка остатка перед добавлением в корзину | ❌ нет (primary)    | 0 сек               | Риск overselling                                    |
| orders    | История заказов пользователя                 | ✅ да               | ≤10 сек             | Некритично для бизнеса                              |
| orders    | Статус заказа после оплаты                   | ❌ нет (primary)    | 0 сек               | Важно для предотвращения повторной оплаты           |
| carts     | Любое чтение корзины                         | ❌ нет (primary)    | 0 сек               | Корзина часто обновляется; нужна актуальность       |

### 4.2 Пример настройки read preference в драйвере

```java
import com.mongodb.ReadPreference;
import com.mongodb.client.MongoCollection;
import org.bson.Document;

MongoCollection<Document> products = database.getCollection("products");

products.withReadPreference(ReadPreference.secondaryPreferred())
        .find(new Document("category", "Электроника"))
        .into(new ArrayList<>());
```

### 4.3 Мониторинг задержки репликации

```javascript
// Команда на вторичной реплике
rs.status().members.forEach(m => {
    print(m.name, "lag:", (m.optimeDate - rs.status().members[0].optimeDate), "ms");
})
```

## 5. Задание 10. Миграция на Cassandra

### 5.1 Выбор сущностей для переноса

| Сущность                         | Причина переноса в Cassandra                                                              | Остаётся в MongoDB                                                       |
|----------------------------------|-------------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| **История заказов** (аналитика)  | Высокая нагрузка на чтение, геораспределение, только вставки, не требует транзакционности | –                                                                        |
| **Сессии пользователей**         | Высокая интенсивность записи/чтения, TTL, не требует транзакций                           | –                                                                        |
| **Заказы** (актуальные, статус)  | –                                                                                         | Требуют транзакций с обновлением остатков (ACID)                         |
| **Корзины**                      | –                                                                                         | Требуют атомарных обновлений массива и слияния                           |
| **Товары** (каталог, остатки)    | –                                                                                         | Сложные запросы с фильтрацией, ACID-обновления остатков                  |

**Дополнительно**: история заказов в Cassandra заполняется **асинхронно** из MongoDB через Change Data Capture (Debezium + Kafka) или фоновым процессом репликации. Это позволяет разгрузить MongoDB от аналитических запросов и обеспечить геораспределённость.

### 5.2 Модель данных в Cassandra (CQL)

#### Таблица `order_history_by_user_bucketed` – история заказов (для аналитики)

```cql
CREATE TYPE order_item (
    product_id uuid,
    quantity int,
    price decimal
);

CREATE TABLE order_history_by_user_bucketed (
    user_id uuid,
    year_month text,                  -- "2025-03"
    created_at timestamp,
    order_id uuid,
    geo_zone text,
    status text,
    total decimal,
    items frozen<list<frozen<order_item>>>,
    PRIMARY KEY ((user_id, year_month), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

**Partition key**: `(user_id, year_month)`  
**Clustering columns**: `created_at`, `order_id`

| Преимущества                                                           | Риски                                                                    |
|------------------------------------------------------------------------|--------------------------------------------------------------------------|
| Равномерное распределение заказов по партициям (разбиение по месяцам). | Нет автоматического удаления старых партиций – нужно приложение или TTL. |
| Заказы одного пользователя за месяц в одной партиции – быстрое чтение. | Сложность запросов «за все время» – потребуется несколько запросов.      |

#### Таблица `user_sessions` – сессии

```cql
CREATE TABLE user_sessions (
    session_id text PRIMARY KEY,
    user_id uuid,
    created_at timestamp,
    expires_at timestamp,
    data text
) WITH default_time_to_live = 604800;  -- 7 дней
```

**Partition key**: `session_id`

| Преимущества                                    | Риски                                                                   |
|-------------------------------------------------|-------------------------------------------------------------------------|
| Быстрый доступ по ключу сессии.                 | Невозможно найти сессии пользователя (если не хранить обратный индекс). |
| TTL на уровне таблицы – автоматическая очистка. | –                                                                       |

### 5.3 Стратегии обеспечения целостности данных

| Механизм                | Описание                                           | Для истории заказов      | Для сессий              |
|-------------------------|----------------------------------------------------|--------------------------|-------------------------|
| **Hinted Handoff**      | Временное сохранение записей для недоступных узлов | ✅ включён                | ✅ включён               |
| **Read Repair**         | Сравнение версий при чтении (вероятностное)        | выключен (или <5%)       | выключен (для скорости) |
| **Anti-Entropy Repair** | Фоновое сравнение Merkle-деревьев                  | еженедельно              | еженедельно             |
| **Consistency Level**   | Уровень согласованности                            | `ONE` (запись/чтение)    | `LOCAL_QUORUM` / `ONE`  |

**Обоснование**: история заказов не является источником истины (источник – MongoDB), поэтому допустима слабая консистентность. Сессии требуют высокой доступности и скорости, поэтому `LOCAL_QUORUM` на запись и `ONE` на чтение.

**Пример настройки CL в драйвере (Java)**:

```java
session.execute(
    QueryBuilder.insertInto("order_history_by_user_bucketed")
        .value("user_id", userId)
        .setConsistencyLevel(ConsistencyLevel.ONE)
);
```

**Периодический ремонт**:

```bash
nodetool repair -pr analytics_keyspace order_history_by_user_bucketed
```

### 5.4 Диаграмма потоков данных

```
Клиент (API Gateway) 
    → (создание заказа) → MongoDB (шардированный) — транзакция: обновление остатка + запись заказа
    → (асинхронная репликация через CDC/Kafka) → Cassandra (order_history_by_user_bucketed) — для аналитики
    → (чтение истории заказов) → Cassandra (быстрые геораспределённые запросы)
    → (сессии) → Cassandra (user_sessions)
    → (товары, корзины) → MongoDB (шардированный)
```

## 6. Метрики мониторинга и действия при проблемах

### 6.1 Метрики для MongoDB (дополнение к разделу 3.1)

| Метрика                             | Действие при превышении порога                                         |
|-------------------------------------|------------------------------------------------------------------------|
| Высокая задержка чтения с secondary | Временно переключить read preference на primary; проверить репликацию. |
| Дисбаланс чанков (>20%)             | Включить балансировщик или вручную переместить чанки.                  |
| Медленные запросы (>100 мс)         | Оптимизировать индекс или пересмотреть шард-ключ.                      |

### 6.2 Метрики для Cassandra

| Метрика                            | Инструмент               | Действие при превышении порога                                                               |
|------------------------------------|--------------------------|----------------------------------------------------------------------------------------------|
| Размер партиции (>100 МБ)          | `nodetool tablestats`    | Изменить схему (бакетирование).                                                              |
| Отклонение в нагрузке между узлами | `nodetool status`        | Пересмотреть распределение токенов (например, `nodetool move` или `rebuild`), добавить узлы. |
| Hinted Handoff backlog             | `nodetool statushandoff` | Проверить недоступные узлы, увеличить время хранения hints.                                  |
```
